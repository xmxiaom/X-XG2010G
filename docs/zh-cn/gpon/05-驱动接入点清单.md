基线：`naoki66/openwrt-pon-drivers` @ master（2026-11-15 克隆）
相关仓库：`airoha-xpon`（内核模块）、`airoha-pon-frontends`（光模块）
用途：这是 ImmortalWrt 固件在 `feeds.conf.default` 里引用的 feed：

**要加 GPON，改的是这个 feed，不是固件仓库本身。**

## 1. 现状：GPON 差在哪一行

`airoha-xpon/src/airoha-xpon-mode.c` 的模式表：

```c
static const struct airoha_xpon_mode_info airoha_xpon_modes[] = {
	{
		.mode = AIROHA_XPON_MODE_GPON,
		.name = "gpon",
		.frontend_mode = AIROHA_PON_FRONTEND_MODE_GPON,
		.control_protocol = AIROHA_XPON_CONTROL_OMCI,
		/* ← 缺 .mac_supported = true; */
	},
	{
		.mode = AIROHA_XPON_MODE_XGPON,
		...
		.mac_supported = true,      /* 其余五个模式都有这一行 */
	},
```

而 `airoha-xpon/src/airoha-xpon-main.c`：

```c
103:	if (!mode || !mode->mac_supported)      → 拒绝启动
201:	if (!mode || !mode->mac_supported || ...) → 拒绝切模式
```

**这就是 GPON 上不去的唯一开关。** 加上 `mac_supported = true` 会让驱动尝试启动 GPON，
但因为下面第 3 节的实现全是空的，会立刻崩或无响应 —— 所以不能只加这一行。

## 3. 真正缺的：GTC / PLOAM 实现（约 900–1000 行）

要新增 `airoha-xpon/src/airoha-xpon-gpon.c`，对标现有的 `airoha-xpon-xgpon.c`（964 行）。
按 XG-PON 的函数骨架镜像，GPON 版需要这一套：

```c
/* ---- 必须实现，名字对齐现有 _xgpon_* 风格 ---- */
int  airoha_xpon_gpon_prepare(struct airoha_xpon *xpon);
int  airoha_xpon_gpon_start_rx(struct airoha_xpon *xpon);
void airoha_xpon_gpon_stop_rx(struct airoha_xpon *xpon);
void airoha_xpon_gpon_restart_mac(struct airoha_xpon *xpon, const char *reason);
void airoha_xpon_gpon_advance(struct airoha_xpon *xpon, u32 phy_events, ktime_t now);
void airoha_xpon_gpon_mask_irqs(struct airoha_xpon *xpon);
void airoha_xpon_gpon_counters_start(struct airoha_xpon *xpon);
void airoha_xpon_gpon_counters_update(struct airoha_xpon *xpon);
void airoha_xpon_gpon_emergency_stop(struct airoha_xpon *xpon, const char *reason);
void airoha_xpon_gpon_note_serial_number(struct airoha_xpon *xpon);
void airoha_xpon_gpon_drain_ploamd_locked(struct airoha_xpon *xpon);
void airoha_xpon_gpon_irq / _phy_irq
void airoha_xpon_gpon_los
```

内部还要有（对照 G.984.3）：

| 子系统 | 要做的事 |
|---|---|
| **GTC 帧** | 下行 PCBd（Psync/Ident/SuperFrame Counter/BWmap/CRC）解析；上行 GTC 突发封装 |
| **PLOAM 状态机** | O1–O7；Upstream_Overhead → SN(Serial_Number_ONU) → Ranging_Time(EqD) → Password → Assign_ONU_ID → Configure_PortID → Encrypted_PortID → Request_Key |
| **测距** | Ranging_Time / EqD 计算与写入（参考 `AIROHA_XGPON_EQD 0x0114`、`_RSP_TIME 0x0108`） |
| **T-CONT / Alloc-ID** | DBA 与 Alloc-ID 表配置（`AIROHA_XGPON_TCONT_ID_CFG 0x0250`） |
| **GEM Port** | GEM 封装/解封装（`AIROHA_XGPON_GEM_PORT_CFG 0x0274`） |
| **加密** | AES-128 前向/后向 key 交换（`AIROHA_XGPON_US_AES_KEY_CTRL 0x0200`） |
| **FEC** | RS(255,239) 前向纠错 |
| **OMCI 通道** | GEM Port 承载 OMCC，交给 `airoha-xpon-omci.c` |

## 4. 寄存器窗口：GPON 有独立的 block，目前完全没用

设备树 `airoha,an7581-xpon-mac` 的 `reg-names` / `reg`：

| reg-name | 基址 | 长度 | 驱动当前状态 |
|---|---|---|---|
| `gpon` | `0x1fb64000` | `0x3e8` | ❌ **从未 ioremap，也未使用** |
| `xgpon` | `0x1fb65000` | `0xff8` | ✅ `AIROHA_XGPON_*`（`regs.h` 305 行） |
| `epon` | `0x1fb66000` | `0x1000` | ✅ `AIROHA_EPON_*` / `AIROHA_GEPON_*` |
| `pon-phy` | `0x1faf0000` | `0x2000` | ✅ `airoha_pon_phy_*` |

`airoha-xpon-main.c:651` 只映射了 `epon`（`xgpon` 同理），**没有 `gpon`**。

要做的：

```c
/* private.h:254 附近，epon_base 旁边 */
void __iomem *gpon_base;

/* main.c:651 附近 */
xpon->gpon_base = devm_platform_ioremap_resource_byname(pdev, "gpon");
```

⚠️ 注意：`gpon` 窗口只有 `0x3e8`（1000 字节），看起来比 `xgpon` 的 `0xff8` 小。
**但 `docs/06` 已通过逆向南实：GPON MAC 的寄存器实际只占 `0x0000–0x03c8`（968 字节），
这个窗口刚好装得下，DTB 不需要修改。** 直接
`devm_platform_ioremap_resource_byname(pdev, "gpon")` 后按
`src/airoha-xpon-gpon-regs.h` 的偏移访问即可（原厂偏移减 0x4000）。

## 6. 最短验证路径（不需要完整实现也能先探路）

在写 1000 行之前，可以先做一个 **20 行的探针**：

1. 映射 `gpon` block，dump 全部 250 个 32-bit 寄存器，存成基线
2. 复用 `epon` 的 1G RX 路径，只把 `AIROHA_GEPON_GPON_MODE` 写 1、PCS 换 `MODE_GPON`
3. 看网卡是否出现 `xgtc_sync` 类似的同步状态、是否有 PLOAMd 帧进入 FIFO

如果第 3 步能看到下行 GTC 帧，说明硬件路径通，剩下的就是协议解析；
如果完全没反应，说明 `gpon` block 必须另外初始化 —— 那时候源码就是唯一的出路。
