## 1. 已经确认的结构

函数入口先做两次状态守卫，再进入主分派：

```
0x13b8c  ldr  gpGponPriv->state
0x13b9c  cmp  w0, #1          ┐
0x13ba0  b.ne ...             │  状态 1/2 且 …
0x13bb4  cmp  w0, #2          │
0x13bb8  b.ne ...             │
0x13bc0  cmp  w0, #3          ┘
0x13bc4  b.eq  0x142dc        ← 特殊出口
```

主分派按状态比较 `#1`–`#7`，与 G.984.3 的 O1–O7 一一对应：

| 比较值 | 语义 |
|---|---|
| `#1` | O1 初始态 |
| `#2` | O2 待机（收到 Upstream_Overhead） |
| `#3` | O3 串号（已发 Serial_Number_ONU） |
| `#4` | O4 测距 |
| `#5` | O5 运营（分支最多，含 `xpon_set_qdma_qos`） |
| `#6` | O6 POPUP（失步） |
| `#7` | O7 紧急停止 |

## 3. 卡点已解决：`.eh_frame` 恢复函数边界

### 问题

`.symtab` 里 466 个函数有名字有大小，但 `0x12948–0x1374c` 之间还有一批
**`st_size = 0`** 的静态函数。拿「下一个有名函数的地址」当边界会跨函数，
把相邻函数的 `panic` / `dump_stack` 混进来，分析结果不可信。

### 解法

解析 `.eh_frame`（0xc3d0 字节，带 `.rela.eh_frame`）的 FDE。
FDE 的 `initial_location` 字段带一条 `R_AARCH64_PREL32` 重定位，
重定位符号给出起始地址，紧随其后的 4 字节是 `address_range` —— 边界和大小都是权威值。

工具：`tools/re_ehframe.py`

```
FDE 共 1634 个，全部有重定位
能补出名字 493 个（对照 symtab），纯匿名 1141 个
```

即整个模块实际有 **1634 个函数**，symtab 只记录了其中 493 个的名字。
产物 `build/fde.txt`：`起始地址 / 大小 / 名字`，可直接用于反汇编定位。

### 8 个原本"未命名子函数"的真实尺寸

| 地址 | 大小 | 由调用点推断的作用 |
|---|---|---|
| `0x133e0` | 48 B | 读取激活状态字段（纯结构体访问，无 MMIO） |
| `0x1362c` | 64 B | 状态推进（在 O3/O4/O5 分支各调一次） |
| `0x136a8` | 88 B | 调 `GET_HIR` + 比较 10/1，判断芯片版本或线路类型 |
| `0x13700` | 40 B | 计时/打点 |
| `0x13728` | 36 B | 计时/打点 |
| `0x134e8` | 60 B | `__tasklet_schedule`，投递收包任务 |
| `0x13410` | 44 B | 同上，另一条投递路径 |
| `0x12ccc` | 260 B | `memcpy` + 多重比较（8/4/2/1），疑似 GEM/T-CONT 表项拷贝 |

之前的误判（把 `panic`/`dump_stack` 算进这些函数）就是因为边界越界，现已纠正。
