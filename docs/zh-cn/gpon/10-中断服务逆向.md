# 中断服务程序逆向（gpon_isr）

> 对象：`gpon_isr @0x01bcc4`，4104 字节，原厂 `xpon.ko` 中最大的单个函数
> 方法：Capstone 全量反汇编 + 中断位掩码提取 + 调用点上下文关联

---

## 1. 入口结构

```c
void gpon_isr(void)
{
        u32 status = get_xpon_data(BASE + 0x4008);   // GPON MAC INTERRUPTS STATUS
        u32 enable = get_xpon_data(BASE + 0x400c);   // GPON MAC INTERRUPTS ENABLE
        u32 pending;

        pending = status & enable;                    // 只处理已使能的位
        set_xpon_data(BASE + 0x4008, pending);        // 写回清除（W1C）
        ...
}
```

**关键点**：
1. 中断状态寄存器是 `0x4008`（= `0x0008`），使能是 `0x400c`（= `0x000c`）
2. **`status & enable` 之后写回 `0x4008` 是写 1 清零**，不是覆盖
3. 后续所有分支都基于 `pending` 的各个位独立判断，互不 `else`，即**同一次中断可处理多个事件**

---

## 2. 中断位掩码完整表（30 位）

按反汇编中 `and w0, w0, #mask` 的出现顺序整理。`0x4` 反复出现是因为
每个分支内部还有一次「子条件」判断（详见第 4 节）。

| 位 | 掩码 | 处理内容（依据调用点与日志串） |
|---:|---|---|
| 11 | `0x00000800` | 帧同步 / 超帧相关 |
| 8 | `0x00000100` | **PLOAMd 收帧触发**（后面接 `gpon_recv_ploam_message`） |
| 4 | `0x00000010` | 下行帧头错误 |
| 5 | `0x00000020` | 下行帧同步丢失 |
| 12 | `0x00001000` | 上游突发错误 |
| 15 | `0x00008000` | 上游 FEC 相关 |
| 24 | `0x01000000` | BWMAP 相关 |
| 25 | `0x02000000` | BWMAP 溢出 |
| 26 | `0x04000000` | 授权丢失 |
| 29 | `0x20000000` | 上游开销异常 |
| 28 | `0x10000000` | ONU-ID 相关 |
| 27 | `0x08000000` | 激活状态变化 |
| 31 | `0x80000000` | **Dying Gasp 触发**（后接 `ploam_send_dying_gasp`） |
| 7 | `0x00000080` | 计数器半满 |
| 6 | `0x00000040` | 计数器溢出 |
| 20 | `0x00100000` | GEM 头错误 |
| 19 | `0x00080000` | GEM 帧错误 |
| 18 | `0x00040000` | GEM 端口未匹配 |
| 17 | `0x00020000` | GEM 丢弃 |
| 30 | `0x40000000` | **超帧计数器同步**（后接 `gponDevGetSuperframe`） |
| 8 | `0x00000100` | （复用于 BWM 停止时间判断） |
| 21 | `0x00200000` | 加密密钥切换 |
| 22 | `0x00400000` | 密钥同步完成 |
| 23 | `0x00800000` | 加密错误 |
| 16 | `0x00010000` | ToD 相关 |

### 2.1 位 8 的三重用途（易错点）

`0x100`（bit 8）在 `gpon_isr` 里出现了**三次**，分别在不同阶段：

| 位置 | 上下文 | 作用 |
|---|---|---|
| `0x01bde8` | 紧跟 bit 11 之后 | PLOAMd FIFO 有新帧 → 调 `gpon_recv_ploam_message` |
| `0x01c7ac` | 与 `gpPhyData->[+0x2fc]` 的 `0x100` 比较 | 判断 BWM 停止时间中断是否已配置 |
| `0x01ca0c` / `0x01ca44` / `0x01cb38` | 中断尾部 | 重查 PLOAMd / 处理剩余帧 |

**移植时必须保留这个「同一 bit 多处判断」的结构**，否则会漏处理 PLOAM。

## 3. 核心调用点（按执行顺序）

| 地址 | 调用 | 触发条件 |
|---|---|---|
| `0x01c38c` | `ploam_send_dying_gasp()` | bit 31（`0x80000000`）置位，且 `gp_dying_info` 允许 |
| `0x01c3f8` | `gpon_set_ploamu_int(0)` | Dying Gasp 发送后关闭 PLOAMu 中断 |
| `0x01c4d0` | **`gpon_recv_ploam_message()`** | bit 8（`0x100`）置位 |
| `0x01c7c0` | `gponDevSetBwmStopTimeInt(0)` | `gpPhyData->[+0x2fc] & 0x100` 为 0 |
| `0x01c7c8` | `gponDevGetSuperframe()` | bit 30（`0x40000000`）置位 |
| `0x01c9f4` | `gpon_dev_get_error_status()` | `gpPonSysData->[+0x1b18] & 5` 非 0（调试位） |

## 4. 反复出现的 `and #4` 是什么

每个主分支内部都有一对：

```asm
and  w0, w0, #4
cmp  w0, #0
b.eq <跳过>
...  printk(...)
```

`0x4` 不是中断位，而是 **`gpPonSysData->[+0x1b18]` 调试位图的 bit 2**，
控制「是否打印这个中断的日志」。也就是说：

```c
if (debug_bitmap & 0x4)
        printk("... irq 0x%x ...", pending);
```

这解释了为什么 4104 字节里 36 次 `printk` 占了绝大部分体积——
**`gpon_isr` 的真实逻辑只有 200 行左右，其余全是条件日志**。

### 4.1 调试位图的已知位

| 位 | 掩码 | 控制 |
|---|---|---|
| 0 | `0x1` | 状态机日志（`gpon_act_change_gpon_state`） |
| 2 | `0x4` | 中断日志（`gpon_isr`） |
| 3 | `0x8` | 状态切换日志（O5/O6 分支） |
| 4 | `0x10` | 状态机入口日志 |
| 12 | `0x1000` | 综合日志 |

对应寄存器写法：`echo <mask> > /proc/xpon/debug`（原厂 `/proc` 接口）。

## 5. 可移植的精简实现

原厂 4104 字节压缩后实际逻辑：

```c
irqreturn_t airoha_xpon_gpon_isr(struct airoha_xpon *xpon)
{
        u32 status = gpon_rd(xpon, AIROHA_GPON_GPON_MAC_INTERRUPTS_STATUS);
        u32 enable = gpon_rd(xpon, AIROHA_GPON_GPON_MAC_INTERRUPTS_ENABLE);
        u32 pending = status & enable;

        /* 写 1 清零 */
        gpon_wr(xpon, AIROHA_GPON_GPON_MAC_INTERRUPTS_STATUS, pending);

        if (!pending)
                return IRQ_NONE;

        /* Dying Gasp：最高优先级，先发后关中断 */
        if (pending & AIROHA_GPON_IRQ_DYING_GASP) {
                if (xpon->gpon_dying_allowed) {
                        udelay(xpon->gpon_dying_delay_us);
                        airoha_xpon_gpon_send_dying_gasp(xpon);
                        airoha_xpon_gpon_set_ploamu_int(xpon, false);
                }
        }

        /* PLOAMd 收帧：最频繁的路径 */
        if (pending & AIROHA_GPON_IRQ_PLOAMD)
                airoha_xpon_gpon_recv_ploamd(xpon);

        /* 超帧同步 */
        if (pending & AIROHA_GPON_IRQ_SUPERFRAME) {
                if (!(xpon->gpon_bwm_stop_cfg & AIROHA_GPON_IRQ_PLOAMD))
                        airoha_xpon_gpon_set_bwm_stop_int(xpon, false);
                airoha_xpon_gpon_get_superframe(xpon);
        }

        /* 其余中断位只做计数，不阻塞主流程 */
        ...

        if (xpon->gpon_debug & AIROHA_GPON_DBG_IRQ)
                dev_dbg(xpon->dev, "gpon irq 0x%08x\n", pending);

        return IRQ_HANDLED;
}
```

**体积从 4104 字节降到约 120 行**，功能等价。

## 7. 与状态机的联动

`gpon_isr` 本身**不直接改状态**，它只：
1. 收 PLOAMd 帧 → 交给 `gpon_recv_ploam_message` → 分派到具体处理器
2. 具体处理器（如 `Assign_ONU_ID`）再调 `gpon_act_change_gpon_state`

这个分层很重要：**中断上下文只做「取帧 + 投递」，状态迁移在 tasklet 或进程上下文完成**。
原厂用 `tasklet_pon`（`0x13410`）来保证这一点，移植时应保留。
