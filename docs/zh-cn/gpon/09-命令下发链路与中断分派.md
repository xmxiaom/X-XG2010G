# 命令下发链路与中断分派（关键突破）

> 这一篇解决的是此前两个 P0 缺口，**结论和最初的猜测相反**，必须记录清楚，避免后续走弯路。

---

## 1. 结论先行

| 原本以为 | 实际 |
|---|---|
| `apply_state_config` 直接写 GPON MAC 寄存器 | ❌ 它通过 `__ECNT_HOOK(0x1a)` 调 **EcoNet 钩子**，钩子实现就在 `xpon.ko` 内（`0xb620`） |
| `sub_0x1b410` 是 PLOAMd 的 MIC 校验 | ❌ 它是**重复帧过滤**（拿新帧与上一帧 `memcmp`） |
| 寄存器序列需要从 `xpon.ko` 逐个挖 | ✅ 挖到了，但入口是「命令码 → 处理函数」的二级分派 |

**最重要的收获**：GPON 的硬件操作不是散落的寄存器写，而是收敛到**一个命令分发器 `0xb620`**，
命令码是 `0x101–0x107` 加 `0x01–0x08`。移植时只需要实现这个分发器，不用逐条追寄存器。

---

## 2. 完整调用链（已全部验证）

```
gpon_act_change_gpon_state(5)              [0x013b18]
   └─ apply_state_config(0x12, {0x80,..,3})  [0x01362c]
        └─ sub_0x135b0({1, 0x12, param})     [0x0135b0]
             └─ __ECNT_HOOK(0x1a, NULL, &pkt)   ← EcoNet 钩子，id = 0x1a
                  └─ xpondrv_hook_dispatch_ops  ← 本模块注册的 64 字节结构体
                       └─ 0x0bd2c  钩子入口（type 分派）
                            ├─ type 0 → 0xb620(cmd_pkt)   ← 命令分发器
                            ├─ type 1 → 0xba68(cmd_pkt)   ← 查询/配置分发器
                            └─ type 2 → 中断分派（GPON/EPON 二选一）
```

### 2.1 钩子结构体（`xpondrv_hook_dispatch_ops`，`.data` 偏移 `0x160`，64 字节）

`.rela.data` 里只有两条重定位，说明这是个稀疏结构：

| 结构内偏移 | 值 | 含义 |
|---|---|---|
| `+0x18` | `0x035c8` | procfs 写处理器（`/proc/xpon/...`） |
| `+0x28` | `0x0bd2c` | **钩子主入口**（EcoNet hook 0x1a 的实际处理函数） |

其余槽位为 0 或由运行时填充。

---

## 3. 钩子入口 `0x0bd2c`（208 字节）—— 三路分派

```c
int xpondrv_hook_handler(struct pkt *p)
{
        switch (p->type) {
        case 0:  return sub_0xb620(p);      // 命令下发
        case 1:  return sub_0xba68(p);      // 查询/配置
        case 2:                              // 中断
                if (((gpPhyData->flags30 & 0x78) >> 3) == 1)
                        gpon_isr();
                else if (((gpPhyData->flags30 & 0x78) >> 3) == 0)
                        eponIsr();
                return 2;
        default:
                panic("invalid hook type %d", p->type);
        }
}
```

### 3.1 关键点：GPON / EPON 靠 `gpPhyData+0x30` 的 bit3–6 区分

```
mode = (gpPhyData->flags30 & 0x78) >> 3;
       mode == 1  →  GPON
       mode == 0  →  EPON
       mode == 10 (0xa) → auto（0xb5d4 里 bfi 写入 0xa）
```

**这正是 `AIROHA_GEPON_GPON_MODE = BIT(31)` 之外的另一处模式标记**，
而且它决定了中断走 `gpon_isr` 还是 `eponIsr`。移植时必须同步维护这个字段。

## 4. 命令分发器 `0xb620`（848 字节）—— 移植的核心

### 4.1 结构

```c
int xpondrv_cmd(struct pkt *p)      // p->[0] = arg, p->[4] = cmd
{
        struct work *w = gpPonSysData + 0xfe80;
        bool ok = sub_0xe8c(w);              // 取锁 / 检查就绪

        if (gpPonSysData->[+8] != 0) {       // 初始化中
                if (gpPhyData->flags30 & 0x80) {
                        if (p->cmd == 0x104) {
                                gpPhyData->flags30 &= ~0x80;
                                xmcs_set_connection_start(1);
                                goto out;
                        }
                }
                goto log_and_out;             // 只打日志，不执行
        }

        switch (p->cmd) {
        case 0x01: case 0x06: case 0x08:
                sub_0xad1c(p->arg, p->cmd);   // → LOS/LOF 检测（见 4.2）
                break;
        case 0x02:
                if (onu_rogue_test) { printk(); sub_0xb5e4(); }
                break;
        case 0x03:
                sub_0xad1c(p->arg, p->cmd);
                break;
        case 0x04:
                break;                        // 空操作
        case 0x05:
                if (!(gpPhyData->flags30 & 1))
                        sub_0xb470(5);        // 复位「无 LOS 未就绪」计数
                sub_0xafa0(p->arg);
                break;
        case 0x07:
                break;                        // 空操作
        case 0x101: xpon_phy_start_rouge_handle();  break;   // 开始流氓 ONU 检测
        case 0x102: xpon_phy_stop_rouge_handle();   break;   // 停止
        case 0x103:
                gpPhyData->flags30 |= 0x80;          // 置「连接建立中」
                xmcs_set_connection_start(0);
                break;
        case 0x104:
                break;
        case 0x105: sub_0xb240(0);  break;    // 见 4.3
        case 0x106: sub_0xb240(1);  break;
        case 0x107: sub_0xb4fc();   break;    // 见 4.4
        default:
                printk("unknown cmd 0x%x", p->cmd);
        }
out:
        sub_0xebc(w, ok);                     // 释放锁
        return 0;
}
```

### 4.2 `sub_0xad1c`（276 字节）—— LOS/LOF 检测

```c
void sub_0xad1c(u32 arg, u32 cmd)
{
        if (xpon_mac_print_open) printk("cmd=%d arg=%d", cmd, arg);

        if (sub_0xaccc() != 0) {              // 检查是否允许
                if (xpon_mac_print_open) printk("...");
                return;
        }

        xpon_los_status = 0;                   // 清 LOS 状态
        mode = (gpPhyData->flags30 >> 3) & 0xf;
        if (mode == 1)
                gpon_detect_los_lof(arg);      // ← GPON 分支
        else if (mode == 0)
                eponDetectPhyLosLof(arg);      // ← EPON 分支
        else
                dump_stack();                  // 模式非法，报错
}
```

**这是 GPON 与 EPON 在物理层检测上的分岔点**，`gpon_detect_los_lof` 是 GPON 专属函数。

### 4.3 `sub_0xb240(flag)`（112 字节）—— MPCP 复位（仅 EPON）

```c
void sub_0xb240(u8 flag)
{
        if (((gpPhyData->flags30 & 0x78) >> 3) != 0)   // 非 EPON 直接返回
                return;
        if (flag != 1)
                return;
        for (i = 0; i <= 7; i++)
                eponMpcpLocalDergstr(i);              // 8 个 LLID 逐个去注册
}
```

**对 GPON 无效**，纯 EPON 逻辑，移植时可直接忽略。

### 4.4 `sub_0xb4fc`（232 字节）—— 连接建立 / 模式回退

```c
void sub_0xb4fc(void)
{
        if (gpPhyData->flags30 & 1)            // 已在连接态
                return;

        if (sub_0xb470(0x107) != 1)            // 见 4.5
                return;

        if (xpon_mac_print_open) printk("...");

        if (gpPonSysData->[+4] == 1)
                xmcs_report_event(1, 5, 0);            // GPON：上报「连接建立」
        else if (gpPonSysData->[+4] == 2) {
                eponSetMpcpDiscStateToDefault();       // EPON：MPCP 回默认
                xmcs_report_event(2, 0x15, 0);
        }

        /* 把 mode 字段改成 0xa（auto） */
        gpPhyData->flags30 = (gpPhyData->flags30 & ~0x78) | (0xa << 3);
        auto_mode();
}
```

### 4.5 `sub_0xb470(cmd)`（140 字节）—— 退避计数

```c
int sub_0xb470(u32 cmd)
{
        if (cmd == 5) {
                phy_no_los_ready_cnt = 0;
                return 0;
        }
        phy_no_los_ready_cnt++;
        if (phy_no_los_ready_cnt % phyNoLosNoReadyHandleCycle == 0) {
                phy_no_los_ready_cnt = 0;
                return 1;                       // 到达周期，允许动作
        }
        return 0;
}
```

**这是「无 LOS 但未就绪」的退避机制**：每 `phyNoLosNoReadyHandleCycle` 次才允许重试一次，
避免在光路异常时疯狂重连。

## 5. 查询/配置分发器 `0x0ba68`（708 字节）

`p->[8]` 是子命令，`p->[0x10]` / `p->[0x18]` 是参数指针。

| 子命令 | 动作 |
|---|---|
| `0` | `xmcs_get_onu_info()` → 填 0x3a 字节结构 → `xmcs_set_sn_passwd()` |
| `1` | 若 `gpPonSysData->[+0] != 1` 则返回；否则把 `p->[0x10]` 单字节交给 `sub_0x1d10` |
| `2` | `p->[0x10]` 单字节交给 `sub_0xb2b0`（GPON）或 `sub_0xb39c`（EPON） |
| `3` | `xmcs_get_onu_type(p+0x10)`，失败打印并返回 -1 |
| `4` | `p->[0x18] = sub_0xb970(p->[0x10])` |
| `8` | 若 `gpPonSysData->[+0] == 1`：`sub_0x1d10(p->[0x10])` |

### 5.1 子命令 1 里的「模式写入」逻辑（重要）

```
if (gpPonSysData->[+0] == 1)                        // 或 mode==1
        *(u8 *)p->[0x10] = 1;                        // 强制 GPON
else if (gpPonSysData->[+0] == 2 || mode == 0)
        *(u8 *)p->[0x10] = 2;                        // 强制 EPON
else
        *(u8 *)p->[0x10] = 0;                        // auto
```

**这就是 `ponctl mode set gpon/epon/auto` 的底层实现**，四个分支对应四种线路模式。

## 6. 对移植的直接影响

### 6.1 工作量重新评估

| 原计划 | 修正后 |
|---|---|
| 逐个还原 110 个寄存器的读写时序 | **只需实现一个命令分发器**（`0x101–0x107` + `0x01–0x08`） |
| 需要理解每个状态迁移的副作用 | 状态机只负责调 `apply_state_config(0x12, ...)`，副作用在分发器里 |
| GPON/EPON 两套独立路径 | 共用一套框架，靠 `flags30` 的 mode 字段分流 |

**结论：工作量比原先估计的少一半以上。** 因为原厂的架构本身就是「命令 → 钩子 → 分发器」的分层设计，
上层（状态机、PLOAM）与下层（寄存器）通过命令码解耦。

### 6.2 必须实现的接口（按顺序）

```c
/* 1. 命令分发器 —— 对应 0xb620 */
int airoha_xpon_gpon_cmd(u32 arg, u32 cmd);

/* 2. 查询/配置分发器 —— 对应 0xba68 */
int airoha_xpon_gpon_query(struct gpon_cfg_pkt *p);

/* 3. 中断分派 —— 对应 0xbd2c case 2 */
irqreturn_t airoha_xpon_irq_dispatch(int irq, void *data);

/* 4. LOS/LOF 检测 —— 对应 0xad1c → gpon_detect_los_lof */
void airoha_xpon_gpon_detect_los_lof(u32 arg);

/* 5. 连接建立 —— 对应 0xb4fc */
void airoha_xpon_gpon_connection_up(void);
```

### 6.3 模式字段的双重维护（易错点）

GPON 模式在**两个地方**有标记，必须同步：

| 位置 | 位 | 作用 |
|---|---|---|
| `gpPhyData->flags30` bit3–6 | `(flags30 & 0x78) >> 3` | 决定中断走 GPON 还是 EPON |
| `AIROHA_GEPON_GPON_MODE` | `BIT(31)` | 1G MAC 的工作模式位 |

只改一处会导致「中断进 EPON 分支但 MAC 按 GPON 工作」的诡异故障。
